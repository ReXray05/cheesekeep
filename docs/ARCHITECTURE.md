# ARCHITECTURE — Godot modular

Fecha: 7 de octubre de 2026. ARCHITECTURE AGENT. Contratos previos a implementación.

## Entorno y escena

Godot 4.4.1 disponible. Orquestador obtuvo plantillas web 4.4.1 en `work/templates/web_release.zip` y `web_debug.zip`; comprobar uso efectivo en exportación. No utilizar templates 4.1.1. Compatibility y export sin hilos si permitido; probar HTTP y documentar requisitos reales. Sin plugins de gameplay/backend/física 3D.

Main/Game organiza estado, input, jugador, economía, mejoras, HUD y audio. Control/HBoxContainer compone paneles laterales y SubViewportContainer cuadrado. SubViewport 360 × 360 se escala a 720 con nearest; contiene World Node2D, suelo, torre, actores, proyectiles, efectos y Camera2D. Arena provisional radio 330 unidades; cámara muestra parte y sigue al jugador. Mundo y distancias son 2D planos, isometría solo visual. Sombras e indicador bajo actores; orden por y. Jugador elevado visualmente sobre queso mantiene posición de suelo.

Input central: transforma cursor local del campo con inversa de canvas/cámara. UI captura izquierdo, pero liberación derecha de carga ya iniciada llega siempre a arco. Último aim válido se mantiene fuera de campo. Shake visual acotado y transformación coherente; origen físico del arco no depende de deformación del sprite. Pérdida de foco limpia input/carga de forma explícita.

## Contratos compactos de implementación

| Componente | Contrato y propiedad |
| --- | --- |
| Game/Main | Orquesta estados, referencias y enlaces; jugador, mundo, input/HUD, economía, mejoras y audio |
| BowController Node | `begin_charge`, `release(direction)`, `tick(delta)`; signals `shot(data Dictionary)`, `snapped`; estado/tiempo/riesgo/cooldown desde config |
| BowVisuals + AimIndicator Node2D | Lee parámetros del arco; dibuja tensión, recoil y triángulo; no decide daño ni RNG |
| ArrowPhysics Node2D | `setup(origin,data)`, integración de segmento, signal `moved_segment(from,to)`, registro IDs impactados y presupuesto de penetración |

| EnemyController Node2D | `configure(kind,wave)`, `take_hit(damage,critical)` retorna Dictionary `killed,blocked,dealt`; `tick(delta,playerPos,towerPos,playerAlive,mounted)`; signals `attack(target,amount)`, `died(reward)` |
| EnemyVisuals | Variante, flash, squash y aviso; no calcula recompensa |
| WaveManager | Datos de composición/spawn, pending/alive y final único; nunca lógica de tienda |

Shot Dictionary inmutable tras release: `direction Vector2`, `speed float`, `damage float`, `critical bool`, `pierce int`, `range float`. Configuración permite tiempo y semianchura para AimIndicator; release muestrea base uniformemente. Main valida/descuenta exactamente una munición antes de instanciar; no se descuenta en visuales. Main procesa moved_segment contra círculos de enemigos ordenados por distancia, llama take_hit y register_hit; este adaptador puede extraerse si crece, sin duplicar física. Contratos acordados antes de trabajo paralelo.

No autoloads inicialmente. Referencias inyectadas por escena raíz y señales para feedback. No búsquedas globales por frame, singletons de cada sistema ni referencias circulares. Si Main crece al integrar MVP, extraer economía/upgrades/input/HUD en componentes pequeños; no crear abstracciones vacías antes de necesitarlas. Prototipo reutiliza componentes y se abre por escena propia o `?prototype=1`, sin fork de código de arco.

## Estados, datos y guardado

MENU → PRE_WAVE → WAVE → UPGRADE_SELECTION → PRE_WAVE. GAME_OVER al destruir queso desde cualquier fase. SHOP es panel siempre disponible, no fase pausante. Muerte/respawn/refugio son estados de jugador. Game valida transiciones: siguiente oleada solo tras elección, GAME_OVER rechaza compras/disparos/spawns. Muerte/rotura/derrota resetean carga y referencias pendientes.

Compras transaccionales: validar saldo, capacidad/utilidad y torre viva antes de descontar/aplicar. Muerte y oleada emiten premio una sola vez. Ratas atacan por cooldown, no contacto cada frame. Reiniciar crea nueva instancia de partida; elimina timers/flechas/actores y señales anteriores.

Resources o tablas tipadas pequeñas centralizan BowConfig, EnemyData, WaveConfig, UpgradeData. Balance solo en una fuente efectiva y documentado en BALANCE. UpgradeData: ID, título, explicación, categoría, max_rank, requisitos, estadística, operación, valor. Estadísticas se recomponen desde bases + rangos, sin volver a multiplicar valores actuales cada vez que se abre UI.

Retención: lista ordenada de adquisiciones válida (padres antes que hijos), conservar prefijo `floor(N*clamp(coins/200,0,1))`; umbral 200 provisional. Reset saldo. JSON user:// versionado guarda ajustes/progreso retenido; validar IDs, rangos, requisitos y archivo corrupto. Almacenamiento web local, sin cloud. Resultado de derrota expone regla al usuario.

Estructura: scenes/{game,player,weapons,projectiles,enemies,ui,effects}; scripts con mismas categorías y waves/economy/upgrades/systems; data/{balance,enemies,waves,upgrades}; assets/{sprites,audio,fonts,effects}; tests; docs; README. Collision layers/máscaras explícitas; flechas afectan enemigos y nunca jugador/torre.

## Robustez y verificación

RNG reproducible para riesgo/ofertas/oleadas. Flechas verifican segmento a alta velocidad, un hit por enemy ID, rango/lifetime/offscreen. Ataques y target selection limitados en frecuencia. Ensayo inicial 80 ratas/50 flechas, spawn respeta techo y reanuda plazas libres; efectos acotados. Objetivo 60 FPS, medir navegador/equipo real. Sin pooling hasta necesidad medida.

Tests significativos: sweet spot, riesgo independiente de dt, varios impactos de segmento, muerte/recompensa única, saldo insuficiente, ofertas/requisitos, wave finish, respawn/gameover/reinicio y retención/corrupción. Smoke headless detecta parse/carga; navegador verifica input, cámara, UI/foco, audio, scaling y guardado. No sustituir playtest con headless.

# ARCHITECTURE V2 — contratos de evolución sobre M13

7 de octubre de 2026. Contrato previo a implementación; no describe funcionalidades ya entregadas. Esta sección prevalece sobre las reglas V1 incompatibles de arriba. Baseline M13: `game.gd` instancia scripts directamente, llama sus `tick` y resuelve impactos por segmentos; se conserva ese modelo, Godot **4.4.1**, renderer Compatibility y exportación web sin hilos con templates de la misma versión. No introducir física 3D, NavigationServer, ECS, autoloads ni reconstrucción general de escenas para esta evolución.

## Propiedad de archivos y dependencias

| Responsable | Propiedad exclusiva | Contratos que consume |
| --- | --- | --- |
| Bow/Arrow | `scripts/weapons/*`, `scripts/projectiles/*` | Config inyectada; no acceso a Economy, Game, Player ni lista de enemigos |
| Player/Input | `scripts/player/*`, `scripts/input/*`, `scripts/systems/persistence.gd`; nuevo `scripts/systems/tower_geometry.gd` y settings si necesita separarse | Config, acciones abstractas y geometría; no calcula daño a enemigos/recompensas ni fases |
| Enemy/Economy | `scripts/enemies/*`, `scripts/economy/*`, nuevo `scripts/pickups/*` | Geometría común; contexto de daño explícito y posición de recogida inyectada |
| Orquestador | `scripts/game/*`, `scripts/ui/*`, `scripts/upgrades/*`, `scripts/effects/*`, oleadas, escenas, datos, proyecto/export y documentación de integración | Todos los contratos de esta sección; único sitio que conecta señales y aplica transiciones |

Cada agente añade tests de sus contratos en archivos propios; no edita `game.gd`, balance compartido o tests de otro agente. Los valores nuevos tienen defaults en componentes hasta integración; la fuente final es `data/balance.json` y los efectos del árbol en `data/upgrades.json`, ambos integrados por el orquestador. Dependencia inicial: acordar aquí APIs → Player publica geometría → Enemy la consume → Game integra. Enemy puede preparar navegación antes de recibir geometría, pero el resultado final usa una sola implementación, sin fallback duplicado. Bow/Arrow puede trabajar independientemente. No commit con archivos ajenos.

## Game, fases y tiempo

Game conserva `phase: String`, con valores únicos `MENU`, `PREP`, `WAVE`, `CHOICE`, `OVER`, y añade `PAUSED` como única capa de suspensión con `resume_phase: String`. Inicio: MENU → nueva partida → PREP → WAVE → CHOICE → PREP; derrota → OVER. PAUSED conserva la fase de retorno sin apilar estados. Ajustes, ayuda y árbol dentro de pausa son vistas del mismo overlay; cerrar una vista vuelve al menú de pausa, no reanuda ni pisa `resume_phase`. Tienda de combate sigue sin pausa. Bootsplash es configuración de Godot, no otra fase. El prototipo puede entrar directamente a PREP.

Game es dueño de `request_pause()`, `resume_game()`, `start_run()`, `return_to_menu()` y de validar todos los callbacks. No ataques, compras, spawns, selección o disparos recibidos por señales atrasadas durante PAUSED/MENU/OVER. Reinicio conserva ajustes y progreso retenido, limpia captura/acciones/actores/pickups y conexiones del run anterior; volver a menú abandona el run sin conceder retención de derrota nueva.

Suspensión preferida: gate central de `tick`, porque los componentes actuales no usan física de SceneTree. En PAUSED no avanzan bow, player, respawn, enemies, arrows, pickups, wave, tiempo de partida, cámara o feedback del mundo. Router/HUD siguen procesando pausa y navegación. Tweens/timers autónomos de efectos y dummy deben pausarse también o convertirse en relojes llamados por Game; el gate de Game por sí solo no congela `create_timer()`/tweens. PREP/CHOICE permiten desplazamiento, recoger y recuperar arco/respawn; sin spawns ni ataques de oleada. OVER/MENU no simulan el run. Esta política debe verificarse también con prototipo y pérdida de foco.

## Input, apuntado, Player y geometría

Router conserva `move_requested(destination: Vector2)`, `start_requested`, `release_requested`, `mouse_world`, `inside`, `captured`, `enabled`, `reset()`. Añade `apply_settings(settings: Dictionary)`, `set_suspended(value: bool)`, `movement_vector() -> Vector2`; señales `melee_requested`, `dash_requested`, `interact_requested`, `pause_requested`. Game conecta acciones sin leer botones físicos. Router transforma cursor con canvas/cámara actual y conserva último cursor válido fuera del campo; solo éste interpreta WASD/E/Espacio/Esc, botón de tiro elegido, botón opuesto de movimiento/interacción y central de melee. Acciones nuevas se admiten únicamente en campo sin UI consumidora; pausa se captura globalmente. Las liberaciones de una carga capturada sí se capturan globalmente. Movimiento WASD se normaliza; clic conserva `go_to(point)`.

`start_requested` es intento, no confirmación: Game verifica fase, vivo, ammo y límite de proyectiles; solo escribe `router.captured = true` si Bow acepta. La captura recuerda el botón que inició el hold aunque cambien ajustes. No remapear mientras una carga está activa. `reset()` borra captura/colas, nunca emite release; se usa en muerte, derrota y reinicio. Suspender no llama Bow.reset ni release, y conserva charge_time. Un mouse-up durante suspensión queda registrado como `pending_release` una sola vez; no dispara automáticamente al volver. Si el botón sigue mantenido, la siguiente liberación normal resuelve; si ya está suelto, una nueva pulsación explícita recaptura la carga existente sin llamar de nuevo a begin_charge ni reiniciar su reloj, y su liberación la resuelve. Pérdida de foco lleva a PAUSED y usa esta misma política. No hay cancelación voluntaria ni avance de carga durante pausa.

Player conserva `go_to(point)`, `tick(delta, charging)`, `hurt(amount)`, `revive()`, `bow_origin()`, campos `direction`, `mounted`, `alive`, `invulnerable`, `moving`. Añade `setup(config: Dictionary)`, `set_movement_input(vector: Vector2)`, `request_interact() -> bool`, `request_dash(direction: Vector2) -> bool`, `request_melee(direction: Vector2, charging: bool) -> bool`, `aim_anchor() -> Vector2`. `aim_anchor` no depende de direction: posición física más elevación estable de arquero/montaje. Game calcula aim desde ese ancla con zona muerta y último aim válido, escribe direction y luego calcula bow_origin para arte/shot. No realimentar bow_origin al cálculo del aim. Cámara suaviza seguimiento en Game; shake va por offset separado, nunca altera posición física o ancla.

Player posee cooldowns, duración, iFrames, perfil/curvatura limitada de dash, ralentización melee y una única solicitud melee en cola durante dash. Game solicita melee únicamente si Bow no está cargando; Player vuelve a validar al ejecutarla al terminar dash. Melee permitido durante COOLDOWN del arco, sin dependencia de ammo. `melee_started(data: Dictionary)` se emite una vez al comenzar el golpe efectivo, con `origin: Vector2`, `direction: Vector2` normalizada, `range: float`, `half_angle: float` en radianes, `damage: float`, `knockback: float`; `melee_finished`, `dash_started`, `dash_finished` alimentan feedback. La ralentización dura la animación; Game resuelve el barrido una vez, no por frame. Dash desde torre desmonta y encadena dash; no monta de forma automática al pasar cerca. Muerte/reset vacían cola y restauran estado.

`tower_geometry.gd` es RefCounted con funciones estáticas, dueño Player/Input: `constrain_motion(from: Vector2, to: Vector2, actor_radius: float, tower_enabled: bool = true) -> Vector2`, `accessible_point(point: Vector2, actor_radius: float = 0.0, tower_enabled: bool = true) -> Vector2`, `tower_contact(point: Vector2, actor_radius: float) -> bool`. Constantes compartidas de arena y huella sólida; márgenes de interacción separados de ocupación. `constrain_motion` barre segmento contra torre y borde, evita tunneling incluso en un frame largo y conserva punto seguro al bloquearse. Player decide rodeo/intención de montar y Enemy decide rodeo/target; ambos usan el mismo límite final para marcha, dash/embestida y empuje. Radios/proyección de pickups usan accessible_point. Excepción de montaje explícita en Player; no abrir un agujero genérico para dash. Visuales/Y-sort resuelven oclusión sin cambiar huella física. Arena/huella nunca dependen del viewport ni de cámara.

## Bow, Shot y Arrow

Bow mantiene `setup`, `value`, `begin_charge() -> bool`, `tick(delta)`, `snapshot() -> Dictionary`, `release(direction)`, `reset()`, señales `shot(data: Dictionary)` y `snapped`. Añade `recovered` al terminar recuperación exclusivamente y `charge_stage_changed(stage: String)` para presentación. Secuencia de stages: `low`, `perfect`, `overcharge`, `spectral`, `final`, después rotura determinista al umbral; stage no reemplaza State IDLE/CHARGING/OVERCHARGING/COOLDOWN. Se elimina RNG de rotura; RNG solo dispersión. Tick que cruza el límite rompe una vez y no puede emitir shot después. Snapshot conserva claves actuales, suma `stage`, `spectral`; `range` sigue siendo longitud visible, sin dictar vida verde+.

Shot Dictionary se duplica al emitir y no se modifica: claves V1 `direction`, `speed`, `damage`, `critical`, `pierce`, `range`; V2 `stage: String`, `spectral: bool`, `range_limited: bool`, `half_width: float`, `lifetime: float` (default seguro 6). `range_limited` solo true en low; `pierce` cuenta impactos totales, con `-1` como ilimitado únicamente para spectral. Verde es critical, spectral nunca critical. Morado apunta a dirección central estable y su half_width describe corredor constante, no cono/dispersión visual falsa. Rojo/final siguen penetración finita y no rompen protección. Bow no consume munición ni crea nodos; `_shoot` en Game valida y consume exactamente una antes de instanciar. Perfect feedback sale tras consumo exitoso, no solo al recibir snapshot verde.

Arrow conserva `setup(origin, data)`, `tick`, `moved_segment(from,to)`, `register_hit(id) -> bool`, `hit_ids`, `shot_data`, `remaining_hits`. Añade `finish(reason: String, at: Vector2)` y señal `finished(data: Dictionary)`; finish es idempotente, emite antes de queue_free. Data final: `position: Vector2`, `reason: String` (`range`, `boundary`, `lifetime`, `hits`, `cleanup`), `hit_count: int`, `recoverable: bool`. Range/lifetime y hits nunca hacen queue_free fuera de finish. Game elimina el culling del viewport V1; calcula límite de área y llama finish(boundary,...). OVER/reinicio usan cleanup sin recompensa.

Arrow tick recorta segmento al alcance restante solo si range_limited; emite moved_segment sin adelantar destrucción. Game recorta al límite de arena antes de resolver candidatos (también recorta al swept endpoint las pruebas de impacto); no hits fuera del área en frames largos. `register_hit` marca cada ID una vez, incrementa hit_count y devuelve agotamiento finito; spectral no decrementa -1. Game llama finish(hits, punto de impacto) al agotarse, nunca queue_free directo. Protegido/bloqueado cuenta como enemigo impactado aunque daño sea reducido. finished.recoverable solo si hit_count=0 y reason es range/boundary/lifetime; Game proyecta punto final al último terreno accesible y crea UNA unidad de flecha física. cleanup no genera recurso.

Game conserva el adaptador `_segment` y ordena candidatos por distancia de entrada en el segmento. Flecha normal usa círculo de enemigo; spectral usa franja barrida con radio enemigo + half_width, terminales definidos por tramo y un hit por ID. No multiplicar daño por frames, duración o número de visuales. Arrow/Bow visuales leen spectral y snapshot, sin decidir daño. La franja de AimIndicator comunica anchura física; V1 triángulo sigue para otros stages.

## Enemy, muerte, Economy y pickups

Enemy mantiene `configure(kind,wave)`, `tick(delta,player_pos,tower_pos,player_alive,mounted)`, `attack(target,amount)`, `summon_requested(kind,at)`, `died(reward)` y retorno de take_hit (`killed`, `blocked`, `dealt`, `broken`). Extiende `take_hit(damage: float, critical: bool, source: String = "arrow") -> Dictionary`, con `source` validado `arrow`, `spectral` o `melee`, y campo `death_source: String` asignado ANTES de emitir died. Default conserva tests/llamadas V1. Añade `apply_knockback(direction: Vector2, amount: float)` mediante geometría; no vuelve a aplicar daño. Game pasa critical=false en melee/spectral; protección se conserva. dead protege daño, bajas, ataques y summons posteriores.

La señal died sigue siendo única autoridad de recompensa de baja: Game conecta con enemigo bound, lee posición/death_source y crea monedas físicas reward; si source=melee crea además pack físico de dos flechas iniciales (configurable). No recompensa también en result.killed. El retorno sirve solo para feedback/knockback y la señal para recursos/score/remoción. Así una rata tocada por melee y flecha en el mismo frame paga una sola vez. Premio de oleada sigue economy.earn directo una vez; monedas de bajas solo se incorporan al recoger, nunca en died.

Economy sigue RefCounted con setup/earn/spend/buy_ammo/consume_arrow y añade `collect(kind: String, amount: int) -> bool`: solo `coin`/`arrow`, amount>0, éxito incrementa la cuenta pertinente sin precio. No accede a world, Player o UI. Reparación transaccional y retención permanecen en Game; saldo para retención excluye recursos sin recoger.

PickupManager nuevo Node2D propietario Enemy/Economy: `setup(config: Dictionary)`, `spawn_pickup(kind: String, amount: int, at: Vector2)`, `tick(delta: float, collector_pos: Vector2, can_collect: bool, collect_radius: float, magnet_radius: float)`, `clear()`; señal `collected(kind: String, amount: int, at: Vector2)`. Game conecta a Economy.collect y feedback. No singleton ni lectura global del jugador. can_collect requiere vivo, en suelo y fase PREP/WAVE/CHOICE; montado no recoge ni magnetiza. Recursos permanecen durante cambios de oleada, muerte/respawn y pausas; se limpian al terminar/reiniciar run, sin moneda/munición gratis.

Manager mantiene registros agrupados y dibuja en lote, no un nodo/tween por unidad de recurso. Merge conserva kind y suma exacta; al alcanzar cap de registros, agrupa con el pack del mismo tipo más próximo o reservado, sin descartar cantidades ni conceder saldo automáticamente. Config limita dibujos/registros, no riqueza. Posiciones se proyectan accesibles; magnetismo mueve hacia el jugador sin atravesar huella sólida; recogida básica cómoda sin exigir clic. Cada registro se elimina/marca recogido ANTES de emitir collected para impedir doble cobro. No despawn con temporizador ni borrado al completar oleada.

## Ajustes, árbol, HUD y feedback

Persistence conserva `retain`, `save(history, settings={})`, `load_history()`. Añade `load_settings() -> Dictionary` y validación/migración del payload versión2. `save` debe preservar settings anteriores si se invoca sin cambios de ajustes; Game usará explícitamente ambos conjuntos al guardar derrota. Guardado de ajustes conserva history retenida cargada, no history del run activo (evita convertir cambios de volumen en progreso permanente). Carga V1 preserva IDs/historia válidos, migra claves conocidas de ajustes y completa defaults; datos corruptos/tipos inválidos/versiones futuras fallan a defaults seguros sin crashear. Renombrado temporal conserva el patrón actual. No guardar partida activa ni saldo.

Settings canónicos: `movement_mode` (`click`/`wasd`), `shoot_button` (`left`/`right`), `music_volume`, `sfx_volume` floats 0..1, `help_enabled`, `effects_enabled` bool. Game carga una vez antes de crear/aplicar UI, Router y Feedback, mantiene copia validada y la pasa a save. Ajustar música no silencia SFX y viceversa. Input no es dueño de audio/persistencia; HUD emite `settings_changed(data: Dictionary)` y Game valida, aplica y guarda. Mantener ajustes al restart/return MENU y al guardar derrota.

UpgradeManager conserva history/ranks, offers/acquire/rebuild y requisitos. Efectos de estilo se expresan como datos y config reconstruida desde base, nunca modificando estadísticas actuales acumulativamente. Campos nuevos de melee/dash/recogida/Bow se inyectan a componentes desde `_apply_upgrades`; vidas/cooldowns en curso no se resetean al abrir árbol. UI dibuja nodos y enlaces de requires; ramas combinables, sin exclusividades inventadas. CHOICE concede una mejora por oleada; si no quedan ofertas, fallback explícito existente sin bloquear PREP.

Compatibilidad de IDs V1 obligatoria: conservar `fast_draw` y `steady_string` y su historial/rangos. fast_draw escala conjuntamente sweet_start/end, spectral_start/end y break_time, manteniendo orden y anchuras positivas. steady_string sustituye su efecto RNG eliminado por ampliación determinista del margen rojo final hasta rotura, con descripción actualizada; no queda una mejora sin efecto ni reaparece rotura aleatoria. Bow recibe umbrales ya recompuestos/validados, no multiplica de nuevo. Melee contra armor conserva reducción V1 a 25% con daño HP positivo para todo golpe válido; garantizar que el árbol no lo redondee a cero. La viabilidad con cero recursos exige probar también enemigos protegidos, no solo básicos.

HUD mantiene señales de compra, reparación, próxima oleada, adquisición y reinicio; añade intentos de start_run/pause/resume/return_menu/settings_changed. HUD presenta phase/resume_phase, estados de arco/cooldowns y saldo real; no simula ni decide elegibilidad autoritativa. Game conecta Bow.recovered a feedback READY, snapped a BREAK, shot crítico exitoso a perfect; señales Player y collected a efectos de dash/melee/recogida. Feedback acotado, sin señales que creen daño o recursos. Menú/pausa/ajustes/ayuda/árbol comparten lenguaje de ventanas original; campo cuadrado y métricas vitales conservan visibilidad al escalar.

## Puertas de integración y riesgos concretos

Antes de integrar: comprobar parse/import Godot4.4.1 y contratos puros por componente. Integración verifica cero ammo/cero coins → melee → baja con monedas/flechas físicas → recogida → disparo; protección verde frente a spectral/melee; muerte única; franja multiobjetivo; miss recovery una vez; proyectil verde+ fuera de viewport pero dentro de arena; dash/embestida/knockback contra torre y borde; montaje/carga/aim a 1–2px y cámara móvil. Guardado V1/settings corruptos, derrota y restart no pierden preferencias. Pausa en carga, dash, respawn, flecha y elección congela relojes y no dispara al volver; UI consume ambos botones configurables. Prueba cinco oleadas+jefe y crecimiento de nodos/recursos, luego navegador real y export reproducible. Medir rendimiento/diversión sin sustituir playtest por headless.

Riesgos a vigilar: firmas nuevas llamadas desde tests V1 (usar defaults); died sin source asignado previamente; mezcla de queue_free V1 y finish que duplica recuperación; ganancia inmediata de monedas V1 que duplica pickups; Input polling que auto-release en pausa; geometría duplicada entre Player/Enemy; cap de packs que pierda riqueza; timers/tweens fuera del gate; save(retained) que borre settings; UI y cambios de config que reseteen cooldown/carga. Las cifras y oferta exacta del árbol quedan para balance dentro de SPEC V2, no requieren nuevos sistemas.
